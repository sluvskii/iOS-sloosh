# Полное название из подсказки не находится: разбор и исправление

## Наблюдение пользователя

На устройстве полный запрос «Человек-паук: Новый день» дал пустую выдачу, хотя
подсказка предлагала это название, а короткий запрос находил проект. Приложенный
`sloosh_logs.txt` содержит запуск и синхронизацию, **но ни одного поискового HTTP
события**. Его нельзя использовать как доказательство конкретного ответа каталога,
фильтрации, кеша или проблем пунктуации. Сам лог с пользовательскими данными в Git
не включен.

## Подтвержденные причины несогласованности

1. Клиент превращал `suggestions[].{id,type,title,...}` в `[String]`, а UI применял
   `.searchCompletion(title)`. Выбор конкретного проекта запускал еще один текстовый
   поиск. Идентичность найденной карточки терялась. Одноименные movie/TV и ремейки
   также теряли различия.
2. В серверном коммите `d6a0b1fb428aff4977ea78dedfa3b995521ddcba` подсказки используют
   наблюдаемый словарь, но `runTitleSearch` не восстанавливает точные известные
   карточки при успешном пустом ответе upstream. `fuzzyTitleCandidates` специально
   исключает равные ключи; `correctionCandidates` также исключает исходный ключ.
   Поэтому точное предложение словаря не гарантирует hit текстового endpoint.
3. Это проверено на **настоящем коде серверного сервиса** с контролируемым каталогом:
   короткий запрос возвращает карточку, полный — пустой ответ; после короткого
   запроса полное название появляется как exact suggestion с ID/type, но полный
   поиск все равно возвращает пусто. Это воспроизведение механизма, не проверка
   текущего production и не объяснение того, почему живой upstream не нашел название.

Воспроизведение (только публичные исходники GitHub + mock; без токенов):

```sh
npm ci --prefix tools/search-audit --ignore-scripts
node tools/search-audit/run.mjs --full-title
```

Зеленый результат этого диагностического инструмента означает воспроизведение
серверного расхождения на закрепленном коммите, а не исправность поиска.

## Изменения клиента

- Подсказка сохраняет карточку с типизированной идентичностью. Такая строка открывает
  Details по исходным ID/type, без повторного текстового поиска. Год и тип помогают
  различать одноименные проекты. Подсказки исправления/истории без проверенного ID
  остаются обычными текстовыми completions; отсутствующий ID не выдумывается.
- Ручной ввод полного названия сначала выполняет исходный поиск. Только после
  успешной окончательной пустой первой страницы, **без активных фильтров и серверной
  коррекции**, допускается точное сопоставление с наблюдавшимися карточками или
  типизированными серверными подсказками этого полного запроса.
- Сопоставление учитывает полное локализованное/оригинальное название с прежней
  нормализацией регистра, ё и пунктуации. Оно не удаляет слова, не выполняет fuzzy,
  не заменяет название франшизным префиксом и не снимает фильтры. Неоднозначные
  точные карточки сохраняются раздельно, не выбирается случайный единственный фильм.
- Полученная точная карточка показывается с подписью «Найдено по точному названию».
  Исходная строка не переписывается, чужая пагинация не подмешивается.
- Карточки наблюдаются только в пределах данного аккаунтного VM-сеанса, максимум
  120; на диск не записываются. Подсказки/восстановление используют общий запрос
  для одной строки (до 30 с), отмену и fencing поколений. Ошибка основного поиска
  не маскируется восстановлением. Поздняя карточка не заменяет новый запрос.

## Диагностика и тесты

Экспортируемый журнал теперь содержит `[CatalogSearch]`:

- транспорт: случайный trace, статический endpoint, попытка, HTTP status, длительность,
  размер ответа, наличие маркера версии;
- декодирование: число карточек, страница/всего страниц, наличие курсора/коррекции;
- repository: сколько карточек пришло и сколько сохранено, versioned/legacy;
- VM: поколение, длина запроса, число фильтров, итоговое число показанных карточек,
  признак exact recovery и типизированных подсказок.

**Не записываются** строки поиска/названия, UID, ID проектов, URL, заголовки запроса,
Bearer-токены, курсоры или тела ответов. Ошибки не логируются сырым текстом.

Расширены реальные Swift DTO/policy/VM-тесты: полный Spider-Man title с пустым
первичным ответом, original-title/пунктуация, typed movie/TV/remake, неизвестный ID,
короткий→полный запрос без обрезания строки, строгие фильтры, ошибка основного
поиска, последующие страницы, недоступные подсказки, отмена/поздний ответ,
безопасное содержимое диагностики и связь typed suggestion UI с Details по ID.

## Оставшиеся границы

Это согласует UI и восстанавливает **известное точное** название; не заменяет
серверный индекс. Если карточка не наблюдалась клиентом, словарь текущего серверного
изолята холодный и внешний поиск не находит полное название, клиент не может
достоверно выдумать ID. На сервере нужен отдельный регрессионный тест и решение
exact-dictionary/alias-resolution, с сохранением фильтров и отказом от ложных
совпадений. Серверный код и production в этой iOS-ветке не менялись.

Проверка на устройстве: открыть подсказку → правильный Details; ввести полное
название вручную после короткого запроса; повторить с новой сессией; убедиться,
что фильтр страны/типа не обходится, а другой одноименный проект не подставляется.
Живой upstream, региональный шлюз и устройство этим mock-воспроизведением не проверены.

## Повторный отчет пользователя: предложения при пустом поле (следующее исправление)

Предыдущая правка пропустила другой источник предложений: `.task` загружал
популярные карточки, затем `setDiscoveryTitles(items.map(\.displayTitle))` снова
превращал их в строки. Нативный список при пустом поле поэтому по-прежнему
заполнял поле названием вместо открытия фильма. Параллельно `query.corrections`
без проверки наличия проектов попадал в UI как обычные completions — отсюда
показанные пользователем транслит и бессмысленная смена раскладки.

Исправлены все клиентские источники предложений:

- Популярные карточки сохраняются целиком (`setDiscoveryMovies`), включая ID/type,
  и сразу поступают в bounded observed-card store. Это также делает доступным
  точное восстановление вручную введенного полного названия из этой полки.
- Единый `catalogSuggestions` объединяет реальные серверные, локально наблюденные
  и популярные карточки; точное совпадение тоже остается в списке. Каждый такой
  пункт открывает одну и ту же типизированную destination через действие VM,
  не меняя строку поиска и не запуская новый title-search.
- Destination закреплена на основном экране NavigationStack, а не вложенным
  NavigationLink внутри исчезающего нативного overlay подсказок. При выборе фильма
  поиск закрывает overlay; нажатие клавиатурного «Найти» тоже закрывает overlay,
  чтобы результаты не оставались за еще одним списком предложений.
- Сырые `query.corrections` не становятся экранными предложениями. Они не доказывают
  существование фильма. Реальные типизированные карточки и уже примененная сервером
  коррекция результатов по-прежнему поддерживаются. В VM есть повторная защита от
  текстовых псевдокарточек из legacy/injected adapter.
- Обычными текстовыми completions остаются только явно помеченные «Недавние запросы»
  пользователя, с иконкой часов. Фильм и прошлый текстовый запрос больше не выглядят
  как один и тот же тип действия. История пользователя не удаляется.
- Добавлены проверки фактического действия VM: пустое поле → популярный фильм →
  destination по ID/type, ноль текстовых запросов; movie/TV с одним номером;
  полный запрос после загрузки популярных; невалидные ID; отсутствие преобразований
  со скриншота в серверном адаптере и UI-policy; изоляция аккаунтов и сохранность
  активной строки/результатов при навигации. Это не замена проверке UIKit/SwiftUI
  фокуса и переходов на настоящем устройстве.

Серверный production и алгоритм его словаря в этой клиентской правке не менялись.
